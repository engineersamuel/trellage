## High issues

### F-001. Unrelated renders restart an active fork readiness probe

**File:** `packages/trellage-launcher/src/guide-ui.tsx:4954-4955`
**Introduced dependency:** `guide-ui.tsx:4761-4768`
**Reported by:** Logic & Correctness / claude-opus-5
**Problem:** The readiness effect now depends on `dispatch`, but `ForkWorker`
creates a new `deliver` function on every render. An unrelated main-screen or
augmentation update therefore aborts and restarts an active fork probe.
Continuous updates can prevent readiness from completing and repeatedly start
probe processes.
**Evidence:** A real Ink/PTy regression held an inventory response, parked its
fork, changed the main recommendation, and returned to the fork. The reviewed
implementation issued six inventory calls for one readiness operation.
**Suggested fix:** Memoize the fork dispatch callback with `dispatch` and
`forkId`. Keep the complete readiness-effect dependency list.
**Fix confidence:** Exact replacement using the existing default React import.
**Human judgment:** None.

```diff
-  const deliver: GuideUiDispatch = (action) =>
-    dispatch({ type: GuideUiActionType.ForkDeliver, forkId, action: action as GuideUiAction })
+  const deliver = React.useCallback<GuideUiDispatch>(
+    (action) => dispatch({ type: GuideUiActionType.ForkDeliver, forkId, action: action as GuideUiAction }),
+    [dispatch, forkId],
+  )
```

**Resolution:** The delivery change uses the equivalent named `useCallback`
import. The same PTY scenario now records exactly one inventory call and no
launch.

## Medium issues

### F-002. Approval exposes a queued, unapproved proposal

**File:** `packages/trellage-launcher/src/guide-goal-augment.ts:291`
**Reported by:** Resource Safety & Reliability / gpt-6-astra
**Problem:** After accepting `Use goal`, the controller publishes the next
queued request. A second proposal replaces the UI's retained proposal before
the provider returns the approved first proposal. The application then rejects
the mismatched goal context instead of applying the valid approval.
**Evidence:** Overlapping proposal callbacks returned the first approved prompt
while leaving the second, unapproved proposal as the last displayed goal.
Controller and SDK-adapter regressions reproduced this mismatch.
**Suggested fix:** Stop request publication after final approval.
**Fix confidence:** Exact replacement for the reported queued-proposal failure.
**Human judgment:** None.

```diff
-    this.options.onRequest(this.pending[0]?.request)
+    this.options.onRequest(this.approvalAccepted ? undefined : this.pending[0]?.request)
```

**Resolution:** The controller also suppresses late publication and further
submissions after approval. Pending callbacks stay parked until the provider
settles the approved outcome; rejecting them earlier could race with approval.
Queued and late proposal cases, plus overlapping SDK proposals, now retain the
displayed approved goal.

### F-003. Graceful SDK stop loses the handle needed for forced termination

**File:** `packages/trellage-launcher/src/copilot-goal-augment-provider.ts:287-302`
**Reported by:** Resource Safety & Reliability / gpt-6-astra
**Problem:** The fallback calls `forceStop()` after a bounded `stop()`. Installed
SDK 1.0.11 clears its child handle before sending SIGTERM and waiting for exit.
If the child survives, the provider times out but `forceStop()` no longer has a
handle to terminate it. Retries can leave owned runtimes running.
**Evidence:** An in-memory reproduction of the installed SDK cleanup methods
observed a null handle, only SIGTERM sent, and a child still running. A provider
regression modeled that handle loss and failed before the correction.
**Suggested fix:** After bounded session abort, disconnect, and deletion,
force-stop the owned isolated runtime without first calling SDK `stop()`.
**Fix confidence:** Exact replacement of the helper body after the ownership
decision stated here.
**Human judgment:** Resolved: this is the interview's owned runtime, and graceful
session cleanup is already attempted before runtime termination.

```diff
-  let stopped = false
-  await runCleanupStep(errors, async () => {
-    const stopErrors = await boundedClose("client stop", timeoutMs, () => client.stop())
-    errors.push(...stopErrors)
-    stopped = stopErrors.length === 0
-  })
-  // A timeout releases our wait, not the SDK process. Terminate it before removing its files.
-  if (!stopped) {
-    await runCleanupStep(errors, () => boundedClose("client force stop", timeoutMs, () => client.forceStop()))
-  }
+  await runCleanupStep(errors, () => boundedClose("client force stop", timeoutMs, () => client.forceStop()))
```

**Resolution:** The delivery change reuses the existing bounded cleanup helper
and removes the redundant stop helper. Regressions cover termination before
staging disposal, force-stop timeout, error aggregation, cancellation, and
preservation of the primary model error.

## Recommendations and delivery follow-up

1. Keep the three corrected contracts and their behavioral regressions.
2. Keep the PR in draft until the fixes, upstream integration, and CI are complete.
3. Preserve native manual-input limits; process startup is not goal activation.

The initial CI run also exposed a terminal-test synchronization error: the
revision case waited for the already-visible word `Revise`, then could send
Enter before the selection redraw. It now waits for the selected marker.
A subsequent CI run exposed the same problem at goal replacement: the test
matched artifact text shared by both screens and sent another Enter too soon.
That transition now waits for the prompt editor's `e edit` control as well.
Both affected UI cases passed in five fresh runs, and the complete guide gate
passed all 30 cases. The lifecycle/state group passed 299 cases. The full
repository suite had passed on the reviewed commit; updated-head CI must pass
before merge. No live model or native activation proof is claimed.
