Trellage — Engineering Plan — Draft

Migrating Trellage to Rust

A phased, strangler-style path from the current Node/TypeScript profile compiler and ~39k lines of Bash orchestration to a Rust toolchain, without breaking locked profile digests, contract tests, or the Docker/`gh` delivery model.

Scope: compiler, CLI, native launchers, orchestration scripts Status: proposal, not started Generated from: repository inventory, this session

TL;DR — Rewrite Trellage in Rust as a six-phase strangler migration: port the Effect-based compiler core first (packages/trellage-cli/src, 9,552 lines), then the CLI shell, then GitHub/release integrations, then the ~39,000 lines of Bash that do the actual orchestration and testing, then native launcher installers, then retire the Node toolchain. No phase changes locked profile digests or the external CLI contract that tests/*.sh exercises.

01 Why this plan exists

The user asked to "plan out migrating Trellage to Rust." Trellage does not currently document a Rust migration goal anywhere in its instructions, READMEs, or CI. The rationale, timeline, and staffing below are therefore assumptions, called out explicitly in §7, not commitments the project has made. Everything else — file paths, line counts, build targets, test names — is read directly from the repository as it exists today.

03 Goals and non-goals

Goal

Preserve every external contract

Locked profile digests, the CLI's observable behavior, and every tests/*.sh black-box contract must keep passing, unmodified, after each phase.

Goal

Strangler, not rewrite

Ship a working Rust binary alongside the Node one at each phase boundary; never have a period where neither builds.

Goal

Single static binary

Replace the Node runtime dependency for the CLI with a compiled trellage binary distributable without npm install.

Non-goal

Rewriting Docker itself

Trellage Sandbox still shells out to docker and gh. Rust changes what issues those commands, not the commands themselves.

Non-goal

Changing profile TOML format

Profile definitions under profiles/*/profile.toml and their lock format are a stable interface this migration must read/write byte-compatibly.

Non-goal

A visible behavior change

This is an implementation-language migration. No new user-facing feature is in scope unless called out separately.

04 Phase sequence

Six phases, mostly sequential. Expand a phase for its scope, exit checks, and what it deliberately leaves untouched.

P0 Foundations→ P1 Compiler core→ P2 CLI shell→ P3 Integrations→ P4 Scripts ⇄ P5 Native launchers→ P6 Decommission Node
P0Foundations & feasibility spikenot started

Scope

  • Stand up a Cargo workspace (e.g. rust/) alongside packages/trellage-cli; decide crate boundaries (compiler core, CLI, GitHub client, TOML/lock types).
  • Pick a TOML crate compatible with the existing smol-toml/toml parsing behavior used for profile.toml and lockfiles; diff output on real profiles under profiles/*.
  • Decide the async/error-handling equivalent to Effect (e.g. tokio + thiserror/anyhow, or a small in-house effect-style abstraction) — this is a load-bearing design decision, not a detail.
  • Prototype one already-small module end to end, e.g. src/platform.ts (28 lines) or src/source-policy.ts (43 lines), to validate the toolchain before committing to larger ports.

Exit check

  • A trivial Rust binary builds via cargo build and runs inside the same mise-managed dev environment as the existing CLI.
  • One ported module produces byte-identical output to its TypeScript counterpart on the same fixture inputs.

Depends on: nothing. Blocks: P1.

P1Port the compiler corenot started

Scope

  • Port, in order of size and centrality: lock.ts (721 lines), materialize.ts (784 lines), profile.ts (639 lines), github-cache.ts (315), inventory.ts (176), profile-discovery.ts (227).
  • Keep the existing TypeScript CLI as the only caller during this phase — the Rust crate is a library, invoked from Node via a thin FFI/CLI shim or reference-tested standalone, not yet user-facing.
  • Re-run the existing Vitest fixtures (packages/trellage-cli/test, 13,255 lines) as golden files against the Rust output for parity, rather than hand-porting every test by feel.

Exit check

  • make profile-compiler and make profile-matrix-test pass unchanged.
  • Locked profile digests for every profile under profiles/* are bit-identical between the old and new compiler on the same source inputs.

Depends on: P0. Blocks: P2.

P2Port the CLI shellnot started

Scope

  • Replace src/cli.ts (330 lines, @effect/cli) and src/render.ts (323 lines) with a Rust CLI (e.g. clap) wired to the P1 crate.
  • Ship a single static trellage binary as an alternative install path alongside the existing Node-based prototypes/trellage/install-trellage.sh, without removing the Node path yet.
  • Re-validate every subcommand's help text, exit codes, and stdout/stderr shape against what tests/*.sh contracts currently assert.

Exit check

  • tests/manifest_contract.sh, tests/profile_compiler_fingerprint_contract.sh, and tests/agent_profile_matrix.sh pass against the Rust binary with zero edits to the test scripts.

Depends on: P1. Blocks: P3.

P3Port GitHub / release integrationsnot started

Scope

  • Port the per-harness release resolvers: codex-release.ts (162), copilot-release.ts (123), claude-release.ts (121), prime-release.ts (160), pi-release.ts (117), plus github-repository.ts (17) and resolvers.ts (117).
  • Choose an HTTP/GitHub client (reqwest + a thin GitHub REST wrapper, or octocrab) that reproduces existing caching semantics in github-cache.ts.
  • Preserve the ephemeral, never-persisted gh auth model described in the project's GitHub delivery rules — this phase must not introduce credential caching or logging.

Exit check

  • make caveman-profile-contract and make engineersamuel-skills-contract pass, proving pinned-skill resolution still works end to end.

Depends on: P2. Blocks: P4, P5.

P4Migrate orchestration scriptsnot started

Scope

  • This is the largest phase by volume: scripts/ (1,967 lines) and the harness/verification scripts it calls, prioritized by which already have a contract in tests/ to prove parity against (e.g. dependency_bootstrap_contract.sh ↔ bootstrap-development-dependencies.sh; harness_contract.sh ↔ scripts/harness).
  • Introduce a Rust xtask-style subcommand set (or extend the P2 binary) for repository automation, rather than a second, separate binary.
  • Leave scripts with no contract coverage for last, and consider writing a contract before porting them, not after.

Exit check

  • Every script in tests/'s coverage list passes against its ported Rust equivalent, run through the same make targets.

Depends on: P3. Overlaps with: P5.

P5Migrate native launcher installersnot started

Scope

  • Port prototypes/trellage-router (the trx router) and the per-harness installer scripts in prototypes/trellage-claude-profiles, trellage-codex-profiles, trellage-copilot-profiles, trellage-grok-profiles, trellage-jcode-profiles, trellage-omp-profiles, trellage-prime-profiles.
  • Preserve the Trellage Native vs. Trellage Sandbox distinction exactly: native launchers isolate state on the host and are not a security boundary (except cdx/grx, which invoke each harness's own OS sandbox) — a Rust rewrite must not blur this line or silently add sandboxing where none is documented.

Exit check

  • make native-profile-router and each make native-*-profile(s) target pass against the Rust-built launchers.

Depends on: P3. Overlaps with: P4.

P6Decommission the Node toolchainnot started

Scope

  • Remove packages/trellage-cli's Node dependency graph (Effect, Vitest, oxlint/oxfmt) once the Rust binary is the only shipped artifact; keep or port the test suite's assertions, not just delete them.
  • Update Makefile, .github/workflows/ci.yml, AGENTS.md, and the CLI-specific instructions file (.github/instructions/trellage-cli.instructions.md) to describe the Rust build/lint/test commands instead of npm scripts.
  • Update README.md's "Fresh Machine Setup" so it no longer tells new users to brew install node to build the compiler.

Exit check

  • make test passes with no Node/npm invocation anywhere in the dependency graph it exercises.

Depends on: P4 and P5 both complete.

05 Risks

🔴 High

Bash is the majority of the system

39,055 lines of shell vs. 24,071 lines of TypeScript. A plan that treats P1–P3 as "the migration" and stops has ported the minority. P4–P5 are not optional cleanup — they are most of the work.

🔴 High

Lock/digest drift

Locked profile digests and the Caveman skill's platform lock must stay bit-for-bit stable. Any change in serialization order, whitespace, or hashing in a rewritten TOML/lock layer silently invalidates every existing lock file.

🟡 Medium

Effect has no drop-in Rust equivalent

The project's own convention is "use Effect for TypeScript application logic where practical." Rust has no single library with the same structured-concurrency-plus-typed-errors model; P0 must pick a deliberate substitute rather than default to bare Result everywhere and lose error context.

🟡 Medium

Docker/gh shellouts remain

Rust changes what issues docker build/docker exec/gh commands, not the commands themselves. Do not scope this as "eliminating shell dependencies" — it doesn't.

🟡 Medium

Contract tests are black-box by design

tests/*.sh exercises the CLI's external behavior, which is good for this migration (it won't need rewriting) — but it also means passing contracts don't guarantee internal correctness of the Rust port; golden-file diffing (P1) is still required.

06 Assumptions this plan makes

The request was "plan out migrating trellage to rust" with no stated motivation, timeline, or team size. This plan assumes:

  • The goal is full replacement of the compiler and the orchestration scripts, since a Rust migration that leaves 39k lines of Bash untouched would not be a meaningful "migration to Rust" — see the corresponding open question in §7 if this scope is too broad.
  • A strangler pattern (old and new coexisting per phase) is acceptable, versus a single big-bang cutover.
  • Existing contract tests in tests/ and Make targets are the source of truth for "still works," rather than a new Rust-native test suite replacing them outright.
  • No calendar timeline, budget, or staffing is assumed or estimated here — none was supplied, and none is fabricated.

07 Open questions

  • Is the intended scope the profile compiler only (P0–P3), or the full repository including Bash orchestration and native launchers (P0–P6)? This plan assumes the latter; confirm before P4 begins.
  • Should the Rust CLI aim for @effect/cli-equivalent structured concurrency, or is a simpler synchronous/blocking model acceptable given Trellage's usage pattern (interactive, single invocation, not a long-running service)?
  • Is there an appetite for a temporary period where both a Node-based and Rust-based trellage binary are documented as install options (P2–P5), or must the switch be atomic?
  • Who owns golden-file generation and review for lock/digest parity in P1 — this is the single highest-risk verification step and needs an explicit owner before it starts.
